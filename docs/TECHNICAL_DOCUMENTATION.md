# Technical Documentation

## 1. Project Summary

`tablet-ioni` is an Ionic + Angular application packaged with Capacitor for Android tablets.

The app does not render the main business UI locally. Instead, it:

1. starts in a native Ionic shell
2. validates device access against a GeneXus backend
3. performs local app login
4. opens the assigned GeneXus page inside a native in-app webview

The repository contains both the Angular source and the Android Capacitor project.

## 2. Technology Stack

- Angular 20
- Ionic 8
- Capacitor 7
- Android native project generated by Capacitor
- `@capgo/inappbrowser` for webview hosting
- `@awesome-cordova-plugins/http` with `cordova-plugin-advanced-http` for native HTTP requests
- RxJS for reactive state and event handling

## 3. Current Application Flow

### 3.1 Startup flow

The actual startup route is `startup`, not `home`.

Flow:

1. App launches and redirects `/` to `/startup`
2. `StartupPage` loads device information for display
3. `AppInitService.initialize()` sends device metadata to the backend
4. Backend returns whether the device is allowed and optionally a redirect URL
5. If allowed:
   - app marks device access as granted
   - app routes to `/login` or `/menu` depending on local login state
6. If not allowed:
   - app routes to `/not-found`

Relevant files:

- `src/app/app-routing.module.ts`
- `src/app/startup/startup.page.ts`
- `src/app/services/app-init.service.ts`
- `src/app/services/device-access.service.ts`

### 3.2 Login flow

Login is handled by `LoginService`.

Flow:

1. User submits username and password from `LoginPage`
2. App calls the GeneXus login API
3. On native Android, login uses the native HTTP plugin
4. Backend response is normalized into `LoginResponse`
5. On success:
   - local login session is stored in `localStorage`
   - cookies from the backend login call are captured
   - session timeout tracking starts
6. App navigates to `/menu`

Relevant files:

- `src/app/login/login.page.ts`
- `src/app/services/login.service.ts`

### 3.3 Opening the GeneXus web app

When the app needs to open a remote GeneXus page, `AppInitService.openWebsite()`:

1. checks network availability
2. merges cookies captured from device-validation and login calls
3. syncs cookies into the webview cookie store
4. opens the remote URL with `InAppBrowser.openWebView()`
5. listens for page load errors, close events, and connectivity changes

This is the main integration point between the native Ionic shell and the remote GeneXus application.

Relevant files:

- `src/app/services/app-init.service.ts`
- `src/app/services/genexus.ts`

## 4. Routing and Guards

Routes:

- `/startup`: device validation entry page
- `/login`: local login page
- `/menu`: local menu shell
- `/contact`: local contact page
- `/home`: protected internal page
- `/register`: device registration page
- `/not-found`: blocked or invalid state

Guard behavior:

- `deviceAccessGuard`
  - sends uninitialized users back to `/startup`
  - blocks unauthorized devices with `/not-found`
- `loginGuard`
  - requires both device authorization and local login session

Relevant files:

- `src/app/guards/device-access.guard.ts`
- `src/app/guards/login.guard.ts`

## 5. Core Services

### 5.1 `AppInitService`

Central orchestration service for:

- startup initialization
- device access validation
- opening and closing the webview
- network failure recovery
- navigation back from the webview

### 5.2 `GenexusService`

Posts device metadata to the device validation endpoint.

Payload:

- `deviceId`
- `manufacturer`

Expected response shape:

- `isAllowed: boolean`
- `redirectUrl?: string`

### 5.3 `LoginService`

Responsible for:

- submitting login credentials
- switching between Angular `HttpClient` and native HTTP
- storing local login session
- capturing backend cookies
- restoring saved login state on app restart

Local storage keys:

- `tablet-login-session`
- `tablet-login-cookie-header`

### 5.4 `RegisterService`

Handles device registration requests and stores the accepted registration locally.

Local storage key:

- `tablet-registration`

### 5.5 `SessionTimeoutService`

Tracks local session expiration for app UX.

Current responsibilities:

- store last user activity timestamp
- track app background/foreground transitions
- show warning toast before expiration
- emit expiration event back to the app shell

Important note:

- this is a frontend/mobile timeout helper
- final session security should still be enforced by the backend

### 5.6 `NetworkService`

Provides a unified online/offline signal using:

- browser `online` / `offline` events
- Capacitor Network plugin on native devices

## 6. State and Persistence

The app uses `localStorage` for lightweight client persistence.

Stored items include:

- login session
- login cookie header
- registration record
- session timeout timestamps

This allows the app to restore local state after restart, but the real source of truth for secure business access remains the backend GeneXus server.

## 7. Environment and Backend Configuration

The backend target is configured in:

- `src/environments/environment.ts`
- `src/environments/environment.prod.ts`

Current main values:

- `BACKEND_ORIGIN = https://system.tkks.co.jp`
- `BACKEND_PATH = tkz_gx18u10_wwp1534JavaPostgreSQL`
- GeneXus object prefix values for login and device access APIs

Environment URLs:

- `apiUrl`: device access endpoint
- `loginApiUrl`: login endpoint
- `registerApiUrl`: registration endpoint
- `websiteUrl`: initial GeneXus page opened in the webview

### Development vs production

Development:

- `environment.ts` uses Angular proxy paths such as `/gx/...`
- `proxy.conf.json` forwards `/gx` to `http://system.tkks.co.jp`

Production:

- `environment.prod.ts` uses absolute backend URLs
- Android builds package the production Angular output from `www/`

## 11. Operational Notes

### 11.1 Cookie handling

The app intentionally captures cookies from native HTTP calls and injects them into the webview.

This is necessary because:

- native HTTP and webview cookie stores are not reliably shared
- GeneXus web pages depend on backend session cookies

### 11.2 Session timeout

Current frontend behavior:

- app tracks inactivity locally
- app can show warning and redirect to login
- active webview behavior differs depending on whether timeout comes from backend or fallback logic

Recommended long-term behavior:

- backend should enforce the real session timeout
- frontend should only provide warning and recovery UX

### 11.3 Device authorization

Business access is not based only on login.

A device must first be validated by the backend through the device access API before protected routes are available.

## 12. Known Issues and Risks

1. The existing technical document was previously outdated; current startup flow is service-driven, not `HomePage`-driven.
2. Environment values are still duplicated across Angular environments, proxy config, and Capacitor allowlists.
3. Production hardening is incomplete:
   - `insecureSsl` is enabled
   - cleartext support is enabled in platform config
   - network security config should be reviewed
4. Cookie/session behavior is tightly coupled to GeneXus backend expectations.
5. Some page labels/messages appear to have encoding issues and may need cleanup.

## 13. Recommended Next Improvements

1. Move backend base URL settings to a more centralized configuration model.
2. Replace insecure SSL and cleartext development allowances before final production release.
3. Add structured logging around:
   - startup device validation
   - login
   - webview open/close
   - timeout events
4. Add a real backend-enforced session timeout and align frontend warning UX to that value.
5. Review Android network security config host entries for correctness.
6. Add CI checks for:
   - `npm run lint`
   - `npm test`
   - `npm run build`
